# 手順 4: 研修生全員でチャットする（共有 DynamoDB に切り替え）

## ゴール

- 自分の EC2 のアプリを、講師が用意した **共有の DynamoDB テーブル** に向ける
- 共有テーブルに自分のアカウントを作り、他の研修生とトークする
- 「どの EC2 から見ても同じ履歴」になる理由と、リアルタイム配信の仕組みの違いを理解する

## 4-0. 考え方

手順 2 までは、チャットの履歴はそれぞれの EC2 の中の PostgreSQL に入っていました。
A さんの EC2 と B さんの EC2 は別のデータベースなので、お互いのトークは見えません。

```
手順 2:  A のブラウザ ──> A の EC2 (API) ──> A の PostgreSQL
         B のブラウザ ──> B の EC2 (API) ──> B の PostgreSQL      ← 別々の履歴
```

共有モードでは、履歴の保存先を全員共通の DynamoDB テーブルに切り替えます。
API は各自の EC2 で動いたまま、読み書きの先だけが変わります。

```
手順 4:  A のブラウザ ──> A の EC2 (API) ──┐
                                           ├──> 共有 DynamoDB テーブル   ← 同じ履歴
         B のブラウザ ──> B の EC2 (API) ──┘
```

> A の EC2 に届いたメッセージは、B のブラウザには WebSocket では届きません。
> WebSocket は同じ API につながっているブラウザ同士にしか配れないためです。
> 共有モードでは、画面が 2.5 秒おきにテーブルを読みに行くこと（ポーリング）で他の EC2 の書き込みを拾っています。
> 本番でこれをやるなら、API Gateway の WebSocket や DynamoDB Streams を使います。

## 4-1. 事前に必要なもの（講師が用意）

- 共有テーブル（名前とリージョンを講師から聞く。例: `handson-chat` / `ap-northeast-1`）
- 自分の EC2 の IAM ロールに、そのテーブルへの読み書き権限が付いていること
- 画像用の共有 S3 バケット（既定 `handson-chat-images-<アカウントID>`）と、EC2 の IAM ロールにその `chat-images/` への読み書き権限が付いていること（`scripts/create_image_bucket.sh`）

> IAM ロールが付いていないと「AWS の認証情報がありません」と表示されます。
> EC2 コンソール → インスタンス → アクション → セキュリティ → IAM ロールを変更 で付けてください。

## 4-2. アプリの設定画面で切り替える

1. いつもどおり `http://<EC2 の IP>/` を開き、デモアカウント（佐藤 あかりなど）でログイン
2. 左下の歯車のアイコン（設定）を押す
3. 「共有 DynamoDB テーブル」を選ぶ
4. テーブル名とリージョンを入力する
5. 「接続テスト」を押し、成功のメッセージが出ることを確認する
   - テーブルが見つからない → テーブル名かリージョンの間違い
   - 認証情報がない / 権限 → IAM ロールを確認（4-1）
6. **「保存して切り替え」** を押す。確認ダイアログで OK
7. 自動的にログアウトし、ログイン画面に「共有テーブル <テーブル名> に接続中」と表示される

## 4-3. 共有テーブルに自分のアカウントを作る

共有モードでは、アカウントも共有テーブル側にあります。デモアカウントはありません。

1. ログイン画面で **「新規登録」** タブ
2. ユーザー名（英数字。他の人と重複しないもの。例: `yamada_t`）、表示名（例: `山田 太郎`）、パスワードを入れて登録
3. 左上の「＋」から、他の研修生を選んでトークを開始。全員を選んでグループを作ると「全員チャット」になります

> 注意: ユーザー名は全員で共有されるので、`test` や `user1` のような名前はぶつかります。

## 4-4. 確かめてみよう

- 隣の人とトークし、メッセージが数秒以内に届くことを確認する（WebSocket ではなくポーリングで届いている）
- 相手が開いた後に自分の吹き出しに **既読** が付く
- 自分の EC2 の API を `docker compose restart api` で再起動しても履歴が消えない（EC2 の中に無いから）
- AWS コンソールで DynamoDB → テーブル → 「項目を探索」を開き、`pk` が `ROOM#...` の行にメッセージが並んでいるのを見る

### 画像はどこに保存されるか

共有モードで送った画像は、各 EC2 のディスクではなく **共有の S3 バケット** に保存されます。
メッセージには `/uploads/<ファイル名>` だけが入り、画面がそれを開くと API が S3 の **署名付き URL**（1 時間有効）へ転送します。
バケットは非公開のままで、EC2 の IAM ロールの権限で読み書きしています。

> ローカルモードで送った画像はこれまでどおり EC2 のボリュームに残ります（他の EC2 からは見えません）。
> 画像が表示されない場合は `curl http://localhost/api/info` の `images.backend` が `s3` になっているか確認してください。

## 4-5. ローカルモードに戻す

左下の歯車のアイコン（設定）から「この環境の PostgreSQL」を選び、「保存して切り替え」を押します。
ローカルの履歴（デモアカウントやそれまでのトーク）はそのまま残っています。

設定画面に入れなくなった場合（共有テーブルが消された等）は、EC2 のターミナルから戻せます。

```bash
docker compose exec db psql -U app -d appdb -c "UPDATE app_settings SET value='postgres' WHERE key='mode';"
docker compose restart api
```

## テーブルの中身（興味がある人向け）

1 つのテーブルに、キーの付け方を変えて複数の種類のデータを入れています（シングルテーブル設計）。

| データ | pk（パーティションキー） | sk（ソートキー） |
|---|---|---|
| メッセージ | `ROOM#<ルームID>` | `MSG#<ULID>` |
| ルーム情報 | `ROOM#<ルームID>` | `META` |
| ルームのメンバーと既読位置 | `ROOM#<ルームID>` | `MEMBER#<ユーザー名>` |
| 自分が参加しているルーム | `USER#<ユーザー名>` | `ROOM#<ルームID>` |
| ユーザー | `USER#<ユーザー名>` | `PROFILE` |
| ログインセッション | `SESSION#<トークン>` | `SESSION`（TTL で自動削除） |

メッセージの ID は **ULID**（先頭がミリ秒の時刻になっている 26 文字）なので、ソートキーで並べると時系列順になります。
「このルームの最新 50 件」が 1 回の Query で取れるように、ルーム ID をパーティションキーにしています。
